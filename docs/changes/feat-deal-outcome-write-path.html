Deal outcome (Won/Lost) + unblocking the "Customer order"

branch feat/deal-outcome-write-path · #397 [24] · reported by the client

The bug

At the "Completed" stage the "Customer order (ERP)" form showed up, but creating an order was impossible — the domain requires outcome === "won", and there was no way to mark a deal "Won" in the UI (the outcome field was only set in the seed; there was no setter in the app). #400 only fixed the error text — the actual dead end remained.

After

An outcome write path was added. On a completed deal — buttons ✓ Won Lost. The order form is now gated by outcome:

  • Completed, no outcome → "Mark the outcome…" + buttons (no order is offered);
  • Won → the "Customer order" form is active, the order can be created;
  • Lost → "no order is placed" + buttons (the outcome can be corrected).

The outcome is written to the deal history as an outcome_set event ("Deal outcome"). The outcome can be changed (correction).

How it was built (clean architecture, TDD)

  1. domain setDealOutcome(deal, outcome) — only at the "Completed" stage (otherwise DealOutcomeError), immutable, changes are allowed;
  2. domain/deal-event — a new event type outcome_set;
  3. use-case makeSetDealOutcome (save + write the event);
  4. server-action setDealOutcomeAction (owner access via dealAccess, catches the domain error);
  5. UI DealOutcomeControls + a gate on the order section in the deal card. Wiring — in composition-root (a self-contained commit).

Repro steps

  1. Open a completed deal with no outcome → the "Customer order" block shows "Mark the outcome" + buttons.
  2. Click "Won" → the "Customer order (ERP)" form appears, the order gets created.
  3. Click "Lost" (or correct it) → no order is offered; the feed shows the "Deal outcome" event.

Gate: npm run verify green (849 tests; +domain/use-case outcome tests). Verified live in the browser on the demo/after stopping a parallel session (its dev server was holding the folder).
