The "Customer order" ERP contract

Required fields · idempotency · the ERP write-rejection error model

What changed

  • The createCustomerOrder contract is finished end to end: exact required fields, the idempotency-key format, a typed ERP rejection. #135
  • Idempotency works on the stub: retrying against the same deal doesn't spawn a second order, it returns the existing one.
  • The shipment date is required (the ERP won't post an order without it): added to the order form.
  • Decisions are recorded in docs/adr/0006-erp-order-contract.md. A real ERP will be wired up later by an adapter (#15) — the interface stays the same.
  • The logic is covered by tests (15 for the order contract); the whole verify suite is green — 366 tests.

Before → after

Aspect Before After
Resubmitting an order every click created a new order (risk of duplicates) an idempotency key — a retry returns the same order, no duplicate
Shipment date wasn't requested — the ERP wouldn't post such an order a required field in the form and in the contract
ERP write rejection not modeled a typed ErpWriteError with a reason → a message for the user, not a 500 crash
Fields / ids / service account a "magic API", fields not documented the contract in ADR-0006: fields, CRM↔ERP ids, a separate write account

How to verify

  1. Open a won deal (the "Won" stage), the "Customer order (ERP)" block.
  2. Pick a product, quantity, a shipment date → "Create order in ERP" → an order number appears.
  3. Click "Create order" again for the same deal → the same number comes back with an "already created" note (no duplicate was created — idempotency).
  4. Try it without a shipment date → the form won't submit (the field is required); on the server such a request is rejected with a clear error.

Right now the number comes from an ERP stub; real numbers will arrive with adapter #15 over the same contract.
