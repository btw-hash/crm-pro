#312 · Working filters on operational screens

Filter chips (previously dead on 9 screens) now actually narrow the table via ?filter= in the URL.

What changed

On operational screens, filter pills were decorative (no handlers). Added a shared client component OpsFilters: clicking a chip writes ?filter=<value> to the URL, the server page reads it and narrows the table, the active chip is highlighted, other query params are preserved. Metrics are calculated over all rows, the table — over the filtered ones.

Before → after

Before

Clicking a chip — nothing. The table doesn't change.

After

A click narrows the table, URL ?filter=, active chip highlighted, the link can be shared.

Chips by screen (tied to real data fields)

Screen Filters Field
My shipments All · Preparing · In transit · Delivered status (groups)
Loading & delivery All · Vehicle assigned · No vehicle driver
Packing All · In queue · In progress · Done status
Defect warehouse All · In defect warehouse · Relabeling · Written off status (relabeling = relabel pipeline)
Assortment All · Grow · Hold · Stop trend (growth/stable/dead)
Procurement All · On track · Partial · Not allocated allocatedQty vs requestedQty
Add-on requests All · With a note note ("Today/Urgent" removed — no such field)
Accounting All no distinguishing field (all in_accounting) — dead chip removed
Shipments All multi-section delivery schedule, no single row list — dead chips removed

Principle: chips are tied only to real fields. Where the field behind the old chip doesn't exist, the chip was reworked or honestly removed (no data fabrication).

Repro steps

  1. Open "Packing" (role: Procurement/Head of sales).
  2. Click "Done" → the table keeps only completed requests; ?filter=done appears in the URL; the chip is highlighted.
  3. "All" → the table is full again, ?filter removed from the URL.
  4. Verified headless: on demo data there are only 4 requests total = In queue 2 + In progress 1 + Done 1.
