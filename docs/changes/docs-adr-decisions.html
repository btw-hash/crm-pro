Architecture decisions — three ADRs

docs-only · status semantics for "what counts as fact" · ERP sync direction · Postgres persistence

What was decided

  • ADR-0003 — status semantics: what counts as a "fact", each fact has a single owner (CRM or ERP). #136
  • ADR-0004 — how the CRM learns about changes in the ERP: cursor-based delta polling, with room to move to events later. #137
  • ADR-0005 — the CRM's target data store: PostgreSQL behind a port, off by default (memory mode). #134
  • Docs only — code, tests, and app behavior don't change. These extend the previously adopted ADR-0002.

ADR-0003 · Status semantics for "what counts as fact"

Closes #136
Question Before After
What "paid" means smeared across the deal stage and the ERP the payment fact is owned by the ERP; the CRM only reads it, never sets it
The "Won" stage implicitly conflated with "paid / closed" won = the sale was won ≠ payment; payment/shipment live in the ERP
Financial statuses in the pipeline risk of turning "paid / shipped" into stages not modeled as stages — read from the ERP into the deal feed
AI-produced data — only becomes a "fact" after a human confirms it

ADR-0004 · ERP sync direction

Closes #137
Question Before After
How the CRM learns about ERP changes it didn't — only read on request, never saw ERP-side changes cursor-based delta polling + idempotency
Dependency on ERP-side changes assumed "events from the ERP" (work on the ERP side) MVP with no ERP-side changes — CRM-driven polling over OData
Moving to events (push) later would require a rewrite a transport swap over the same delta model, without breaking the contract

ADR-0005 · PostgreSQL persistence

Closes #134
Question Before After
Where CRM data lives in memory — a restart loses everything a target PostgreSQL store behind a port (Prisma)
Enabling the DB — the PERSISTENCE_MODE flag, defaulting to memory — dev/demo without a DB
Numbers / prices / stock levels — not stored in the DB — come from the ERP (ErpGateway)

Enabled through a separate rollout (see ADR-0005 §"Rollout"); until staged, the DB stays off and day-to-day work doesn't change.
